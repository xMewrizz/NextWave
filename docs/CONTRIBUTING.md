# Правила разработки

## Единица работы

Одна задача из [ROADMAP.md](ROADMAP.md) выполняется в отдельной короткой ветке. Pull request закрывает один проверяемый результат и не смешивает документацию, данные, модель и интерфейс без необходимости.

Примеры веток:

- `feat/v1-03-dataset`
- `feat/v1-04-labels`
- `feat/v1-05-sources`
- `fix/source-timeout`
- `release/v1-qualification`

## Pull request

Описание содержит:

- проблему и итоговое поведение;
- изменённые контракты и версии данных;
- выполненные проверки;
- измеренные результаты;
- известные ограничения;
- ссылку на задачу бэклога.

Утверждение о точности, работающем источнике или развёртывании сопровождается командой воспроизведения и сохранённым артефактом.

## Владельцы

- ML Engineer: данные, разметка, признаки, модель, оценка, candidate gate и decision policy.
- Software Engineer: коннекторы, snapshots, provenance, хранение, API, интерфейс и развёртывание.
- Команда: правила Evidence Duel, спорные метки, исторический срез и выпуск.

Изменение общей схемы Candidate, SourceDocument, EvidenceClaim или FeatureVector проверяют оба технических владельца.

## Проверки

Корневой пакет:

```powershell
python -m unittest discover -s tests -v
python -m compileall -q src tests
python -m nextwave --version
```

Backend:

```powershell
python -m pip install -e . ./backend httpx pytest pytest-asyncio
python -m pytest backend/test_api.py backend/test_job_store.py backend/test_result_store.py
```

Frontend:

```powershell
cd frontend
npm ci
npm run lint
npm run build
```

Тест добавляется для существенного контракта, граничного случая, утечки данных или отказа внешнего источника. Тест, построчно повторяющий реализацию, не добавляется.

## Данные

В проекте различаются:

- `organizer_positive` — 100 положительных строк организаторов;
- `team_model_negative` — проверенные mature и marketing_hype;
- `noise_control` — объекты для проверки candidate gate;
- `runtime_snapshot` — ответы открытых источников для конкретного запуска;
- `test_fixture` — минимальные искусственные данные только для тестов и UI-контракта.

Правила:

- исходные файлы не перезаписываются;
- каждый набор получает checksum и manifest;
- метка хранит автора, дату, cutoff, правила разметки и доказательства;
- черновики и test fixtures не обучают модель;
- связанные технологии получают общий `group_id`;
- организаторские объяснение, стадия, тренд, балл и ссылки не входят в модель;
- сведения после cutoff не влияют на исторические признаки;
- ответы коннекторов сохраняются до очистки и дедупликации;
- большие корпуса, модели, индексы и локальные базы не коммитятся;
- ключи API не попадают в код, логи и snapshots.

## Разметка

Разметчик сначала определяет, является ли объект конкретной технологией. Шум маркируется для candidate gate. Только пригодный технологический кандидат получает один из модельных классов: weak_signal, mature или marketing_hype.

Второй участник независимо проверяет выбранную долю строк без просмотра первой метки. Разногласие разрешается по зафиксированным правилам. Исправление не стирает исходное решение.

## Источники и Evidence

- Один URL не равен одному независимому доказательству.
- Один DOI, патент или canonical URL создаёт один origin.
- Существенное утверждение содержит документ, фрагмент и locator.
- Материал уровня D не является единственным основанием `main`.
- Автоматический перевод и генеративное резюме отмечаются.
- Неизвестная дата исключает документ из временной динамики.
- Ошибка коннектора создаёт `unknown`, а не ноль.

## Эксперименты

Эксперимент фиксирует:

- версии положительного и отрицательного корпусов;
- версию snapshots и feature builder;
- список признаков;
- алгоритм, параметры и seed;
- групповые folds;
- out-of-fold предсказания;
- метрики и confusion matrix;
- ошибки по классам и технологическим областям;
- версию порога и decision policy.

Все модели сравниваются на одинаковых folds. Fit-зависимые преобразования выполняются внутри обучающей части. Результат после изменения признаков, порога или данных получает новую версию. Лучший случайный прогон не выбирается вручную.

## Выпуск

Квалификационный релиз фиксирует:

- Git commit;
- checksums и manifests данных;
- версии разметки, snapshots и folds;
- feature version, модель и порог;
- отчёт метрик и out-of-fold предсказания;
- демонстрационный запрос и сохранённый snapshot;
- исторический срез;
- команду чистого развёртывания;
- известные ограничения.

После release candidate принимаются только исправления ошибок, блокирующих сдачу или воспроизводимость.
