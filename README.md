# NextWave

NextWave — сервис поиска зарождающихся научно-технологических трендов по свободному запросу. Система собирает датированные материалы из открытых источников, объединяет упоминания одной технологии, оценивает её развитие и показывает проверяемые основания включения или исключения кандидата.

Проект создаётся для задачи Газпромбанк.Тех на международном хакатоне 2026 года. Квалификационный релиз запланирован на **29 сентября 2026 года**.

## Результат для пользователя

Пользователь вводит направление, например `технологии в ИИ`, и получает ранжированный список из 15 слабых сигналов. Для каждого кандидата сервис показывает:

- название и описание технологии;
- оценку бинарной модели, порог и ведущие факторы «за» и «против»;
- доказательства ранней стадии, роста и независимого интереса;
- контраргументы: массовое внедрение, стандарт, сформированный рынок, рекламную волну или зависимые публикации;
- проблему, потенциальное преимущество и подтверждённый кейс;
- датированные источники с типом, языком и уровнем доверенности;
- причину включения в основной список либо исключения.

Если после проверки остаётся меньше 15 кандидатов, сервис показывает фактическое число и причины недостатка. Для квалификационной демонстрации заранее проверяется запрос, на котором система формирует полный ТОП-15 без подстановки заранее заданного списка.

## Метод

Единица анализа — технологический кандидат, а не отдельная статья. Обработка состоит из семи этапов:

1. Сбор материалов по открытому запросу.
2. Извлечение конкретных технологий и объединение синонимов.
3. Исключение нерелевантных, слишком широких и дублирующих объектов.
4. Повторный поиск датированных материалов по каждому кандидату.
5. Расчёт тех же признаков, которые использовались при обучении модели.
6. Проверка зрелости, маркетингового хайпа и информационного эха.
7. Формирование ТОП-15 и карточек с доказательствами.

Ключевая особенность NextWave — **Evidence Duel**. Система собирает две группы проверяемых утверждений: основания считать технологию слабым сигналом и основания считать её зрелой, переоценённой или недостаточно подтверждённой. Anti-echo связывает перепечатки с общим первоисточником, поэтому десять копий одного пресс-релиза не становятся десятью доказательствами.

Исторический срез показывает, какой результат система получила бы только по материалам, доступным на выбранную дату. Документы, опубликованные позднее, используются для проверки дальнейшей траектории и не влияют на исходную оценку.

## Данные и модель

Таблица организаторов содержит 100 подтверждённых слабых сигналов. Они образуют положительный класс. Поля «Почему это слабый сигнал», «Стадия развития», «Тренд упоминаний» и балл `3–7` сохраняются как экспертные аннотации, но не передаются бинарной модели.

Команда формирует два отдельных проверочных набора:

- **модельные отрицательные примеры:** зрелые технологии и маркетинговый хайп, сопоставимые с положительными примерами по областям, дате среза и покрытию источников;
- **контроль информационного шума:** слишком широкие, нерелевантные и ошибочно извлечённые объекты для проверки входного фильтра.

Исторические признаки рассчитываются автоматически по датированным документам. Один feature builder используется для организаторских строк, отрицательных примеров и новых кандидатов. Организаторские объяснения и вручную выбранные ссылки не заменяют этот расчёт.

Основная оценка проводится через stratified grouped 5-fold cross-validation. Отчёт содержит Accuracy, Precision, Recall, F1, confusion matrix, ошибки по типам отрицательных примеров и результаты по технологическим областям. Внутренняя цель — Accuracy не ниже 80%. Метрика на самостоятельно собранном корпусе обозначается как внутренняя и не выдаётся за результат на закрытой выборке организаторов.

Для каждого live-кандидата модель сохраняет полный аддитивный разбор logit:
intercept, значение признака после преобразования, коэффициент и локальный вклад.
Ведущие положительные и отрицательные вклады показываются как ключевые
предикторы, а их полная сумма обязана воспроизводить `model_score`. Пока отдельная
калибровка не выполнена, интерфейс называет число «оценкой модели», а не
вероятностью или процентом уверенности.

## Граница MVP

Квалификационная версия должна воспроизводимо показать:

- импорт 100 положительных строк без изменения исходного XLSX;
- проверенный корпус зрелых и хайповых отрицательных примеров;
- отдельную проверку фильтра информационного шума;
- общий расчёт исторических признаков до заданной даты среза;
- бинарную модель и групповой отчёт качества;
- живой поиск по открытым источникам без списка заранее заданных технологий;
- Evidence Duel, anti-echo и причины исключения зрелых кандидатов;
- один заранее зафиксированный исторический срез;
- русскоязычную выдачу ТОП-15 с проверяемыми источниками;
- запуск на стандартном ноутбуке через Docker Compose.

## Текущий статус

Готовы каркас Python-пакета, демонстрационные API и web-интерфейс, базовые доменные контракты, Docker-конфигурация, адаптер положительного класса организаторов, протокол экспертной проверки, неизменяемые snapshots и коннекторы OpenAlex, Crossref и Exa. Exa используется для candidate-level отраслевого enrichment, но не генерирует и не отбрасывает кандидатов до модели. Интерфейс пока использует явно обозначенный синтетический набор и не считается результатом модели.

Discovery, Candidate Gate, aliases, snapshots, candidate-level OpenAlex/Exa
enrichment, point-in-time признаки, frozen inference и resumable Evidence executor
реализованы. Gate проверяет только конкретность и релевантность технологии;
бинарная модель отдельно отличает weak signal от reviewed mature/hype. Один
реальный запрос по инфраструктуре ИИ дал 137 Gate-accepted кандидатов; все они
получили scientific+industry enrichment и frozen model score. Все 137 прошли
постраничную Evidence-проверку: 127 завершены, 6 не имели пригодного входа и 4
закончились ошибкой модели. Офлайн-команда `analysis-result` объединяет эти
страницы, формирует `main/watchlist/excluded`, Evidence Duel и финальный TOP-15;
кандидаты с незавершённой Evidence-проверкой остаются в `watchlist`. Текущий
реальный прогон имеет статус `development_only`, потому что финальный
квалификационный корпус 50 mature + 50 hype ещё не собран. Его `model_score`
некалиброван и не показывается как вероятность или уверенность.
получили scientific/industry coverage, модельную оценку и постраничную
Evidence-проверку. Ограничение 30 относится к одной рабочей пачке и не отбрасывает
остальных кандидатов.

Текущий model report остаётся `development_only`: 100 organizer positives
сопоставлены с 57 mature и 7 ранее принятыми hype, поэтому Accuracy 0.915 нельзя
называть официальной оценкой на скрытом ground truth. Query inference v2 сохраняет
неизменившиеся scores, локальные вклады признаков и глобальные коэффициенты.
Единый финальный JSON, decision policy по объединённым Evidence-страницам,
реальный backend/frontend, PostgreSQL и финальная Docker-репетиция ещё не готовы.

## Локальная проверка основы

Windows PowerShell:

```powershell
py -3.13 -m venv .venv
Set-ExecutionPolicy -Scope Process -ExecutionPolicy RemoteSigned
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -e .
python -m unittest discover -s tests -v
python -m nextwave --version
```

Живой новостной поиск Media Cloud использует временный командный ключ из `config/hackathon.env`. Docker Compose передаёт его только backend автоматически: пользователю клонированного приватного репозитория не нужно регистрироваться во внешнем сервисе или настраивать `.env`. Ключ не включается во frontend, URL запросов, snapshots и логи; после завершения оценки он отзывается. Локальный `.env` остаётся игнорируемой Git настройкой разработчика и подхватывается автоматически: приоритет сверху вниз — переменные процесса, затем `.env`, затем файл настроек.

По умолчанию Media Cloud ищет в дефолтном охвате `NEXTWAVE_MEDIACLOUD_COLLECTION_IDS=34412234,34412118`: API story-list без параметров `ss`/`cs` всегда отвечает 422 (доказано живым прогоном 22.09.2026), глобального поиска без коллекций у него нет. Backend может переопределить набор через ту же переменную; пользовательский интерфейс эту настройку не запрашивает. Английская и русская выдачи загружаются отдельными запросами и объединяются только на уровне кандидатов.

В query-specific candidate enrichment после Gate используется Exa: все принятые кандидаты без предварительного pruning получают отдельные запросы по предыдущему и недавнему временным окнам. Exa возвращает новостные highlights вместе с метаданными, поэтому тот же сохранённый документ можно использовать для построения признаков и последующей Evidence-проверки. Перед признаками фиксированная source policy отделяет новостные, корпоративные, пресс-релизные и блоговые страницы от академических репозиториев; исключённые Exa-документы остаются в аудите. Команда `analysis-enrichment-merge` объединяет научные документы OpenAlex с допустимым Exa-контуром. Media Cloud остаётся в старых воспроизводимых артефактах и discovery-контуре; его сохранённый результат служит базой сравнительного replay, а не скрыто смешивается с Exa.

## Проверка LLM-контура

Query Resolver, извлечение кандидатов, Candidate Gate и labeling Evidence executor используют
явно настроенные YandexGPT-модели: основная пара `NEXTWAVE_LLM_PROVIDER/MODEL` —
`YandexGPT Lite 5`, Candidate Gate — отдельная пара
`NEXTWAVE_GATE_LLM_PROVIDER/MODEL` с `YandexGPT Pro 5`, а labeling Evidence —
`NEXTWAVE_EVIDENCE_LLM_PROVIDER/MODEL` с `YandexGPT Pro 5.1`. Это три фиксированные
конфигурации, а не автоматический routing и не скрытый fallback; пользователь
интерфейса ничего не выбирает и не вводит. Провайдер и модели зафиксированы в
`config/hackathon.env`; API-ключ и ID
каталога являются серверными секретами и не передаются во frontend, prompt, snapshots или
логи. Query Resolver может повторить только повреждённый JSON через `YandexGPT Pro 5` и
сохраняет фактически ответившую модель. Остальные этапы, включая labeling Evidence,
не выполняют скрытый fallback:
ошибка становится `review` или неизвестным покрытием.
Labeling Evidence дополнительно проверяет точную пару `yandex / YandexGPT Pro 5.1`
до создания work и запрещает запуск на общей Lite-модели. При локальном запуске
нужно использовать `config/hackathon.env`; секреты из `.env` подхватываются
автоматически, поэтому передавать `.env` через `--env-file` нельзя.

CLI читает настройки слоями: `config/hackathon.env`, затем локальный `.env`, затем переменные
процесса. Команда проверки:

```powershell
python -m nextwave query-resolve --query "Технологии в ИИ"
```

Для live-запуска backend должен получить `NEXTWAVE_LLM_API_KEY` и
`NEXTWAVE_YANDEX_FOLDER_ID`. В развёрнутом сервисе эти значения задаются один раз на сервере;
пользователь интерфейса ничего не регистрирует и не вводит. Тесты и синтетический UI не
требуют доступа к YandexGPT.
Docker Compose сейчас
запускает демонстрационный backend. Полный discovery-конвейер запускается CLI-командой
`discovery-run` с сохранением сейфа (план, результат, опись); подключение конвейера
к web backend ещё не реализовано.

Результат содержит исходный и нормализованный запрос, варианты поиска, ширину намерения,
провайдера, модель, рассмотренные элементы таксономии OpenAlex и выбранный `subfield` или
`topic`. Ключ не выводится и не сохраняется. Другой файл настроек можно передать через
`--env-file`.

## Сборка организаторского датасета

Исходный файл поместите в `data/raw/organizer_signals.xlsx`, затем из корня репозитория выполните:

```powershell
python -m nextwave dataset-build --input data/raw/organizer_signals.xlsx
```

Команда проверяет лист, заголовки, 100 строк, нумерацию, обязательные значения, области, баллы и отсутствие формул. Только после полной проверки она создаёт новый каталог `data/processed/organizer-positive-2026-09-15-v1` с файлами:

- `positive_candidates.jsonl` — идентификационные поля и положительная метка;
- `positive_annotations.jsonl` — экспертные поля, запрещённые для входа бинарной модели;
- `manifest.json` — версии, диапазон строк, соответствие столбцов, размеры и SHA-256.

Существующий каталог результата не перезаписывается. Для отдельной проверочной сборки можно указать другой новый путь через `--output`.

## Экспорт очереди разметки

После одного или нескольких `discovery-run` соберите очередь экспертной проверки:

```powershell
python -m nextwave labeling-export --runs data/development/discovery/<run_id> --output data/development/labeling-export-v1
```

Команда читает слоты из `templates/labeling_workbook.xlsx`, раскладывает кандидатов, шум и черновики доказательств из сейфов и публикует новый каталог: заполненная книга, `negative_candidates.jsonl`, `noise_controls.jsonl`, `manifest.json` с версиями, составом, дефицитами и контрольными суммами. Шумовые слоты задают только ID и плановый тип (строгие квоты 10/10/10/10/10); фактические область и scope каждой строки берутся из discovery-прогона выбранного объекта и распределяются round-robin между доступными областями. Повтор из тех же входов даёт те же JSONL, книгу и опись побайтово (метки времени zip нормализованы при экспорте); существующий каталог не перезаписывается. В книгу попадают только голубые клетки, метки ставит человек.

## Данные и секреты

Исходный датасет, собранные документы, обученные модели, локальные базы и постоянные секреты не коммитятся. Для приватного квалификационного репозитория временные отзываемые ключи хакатона хранятся только в `config/hackathon.env`, не передаются во frontend и отзываются после оценки. Контактный email для вежливого пула OpenAlex (`NEXTWAVE_OPENALEX_MAILTO`) секретом не является: он штатно уходит открытым параметром запроса. Бесплатный ключ OpenAlex (`NEXTWAVE_OPENALEX_API_KEY`) повышает дневной бюджет: он хранится только в локальном `.env`, отправляется заголовком `Authorization: Bearer` вместе с mailto и никогда не попадает во frontend, URL, snapshots, manifests, результаты или логи. Ключ Exa (`NEXTWAVE_EXA_API_KEY`) также хранится только локально и отправляется заголовком `x-api-key`; он не входит в тело запроса, request identity, snapshots, manifests или сообщения ошибок. Релиз фиксирует checksum исходных данных, версии разметки, признаков и модели, параметры оценки и команду воспроизведения результата.
