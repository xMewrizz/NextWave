# NextWave

NextWave — сервис поиска зарождающихся научно-технологических трендов по свободному запросу. Система собирает датированные материалы из открытых источников, объединяет упоминания одной технологии, оценивает её развитие и показывает проверяемые основания включения или исключения кандидата.

Проект создан для задачи Газпромбанк.Тех на международном хакатоне 2026 года.

## Быстрый запуск

Нужен Docker Desktop с запущенным Linux Engine. Из корня репозитория:

```bash
docker compose up --build -d
```

Откройте `http://localhost:8080`. По умолчанию приложение показывает проверенный
snapshot реального анализа без внешних API-вызовов и без ключей. Healthcheck:

```bash
curl http://localhost:8000/api/health
```

Остановка: `docker compose down`. Подробности, смена портов и live-режим описаны
в [DOCKER.md](DOCKER.md).

## Результат для пользователя

Пользователь вводит направление, например `технологии в ИИ`, и получает ранжированный список из 15 слабых сигналов. Для каждого кандидата сервис показывает:

- название и описание технологии;
- оценку бинарной модели, порог и ведущие факторы «за» и «против»;
- доказательства ранней стадии, роста и независимого интереса;
- контраргументы: массовое внедрение, стандарт, сформированный рынок, рекламную волну или зависимые публикации;
- проблему, потенциальное преимущество и подтверждённый кейс;
- датированные источники с типом, языком и уровнем доверенности;
- причину включения в основной список либо исключения.

Если после проверки остаётся меньше 15 кандидатов, сервис показывает фактическое число и причины недостатка. Для квалификационной демонстрации заранее проверяется запрос, на котором система формирует полный ТОП-15 без подстановки заранее заданного списка.

## Метод

Единица анализа — технологический кандидат, а не отдельная статья. Обработка состоит из семи этапов:

1. Сбор материалов по открытому запросу.
2. Извлечение конкретных технологий и объединение синонимов.
3. Исключение нерелевантных, слишком широких и дублирующих объектов.
4. Повторный поиск датированных материалов по каждому кандидату.
5. Расчёт тех же признаков, которые использовались при обучении модели.
6. Проверка зрелости, маркетингового хайпа и информационного эха.
7. Формирование ТОП-15 и карточек с доказательствами.

Ключевая особенность NextWave — **Evidence Duel**. Система собирает две группы проверяемых утверждений: основания считать технологию слабым сигналом и основания считать её зрелой, переоценённой или недостаточно подтверждённой. Anti-echo связывает перепечатки с общим первоисточником, поэтому десять копий одного пресс-релиза не становятся десятью доказательствами.

Исторический срез показывает, какой результат система получила бы только по материалам, доступным на выбранную дату. Документы, опубликованные позднее, используются для проверки дальнейшей траектории и не влияют на исходную оценку.

## Данные и модель

Таблица организаторов содержит 100 подтверждённых слабых сигналов. Они образуют положительный класс. Поля «Почему это слабый сигнал», «Стадия развития», «Тренд упоминаний» и балл `3–7` сохраняются как экспертные аннотации, но не передаются бинарной модели.

Команда формирует два отдельных проверочных набора:

- **модельные отрицательные примеры:** зрелые технологии и маркетинговый хайп, сопоставимые с положительными примерами по областям, дате среза и покрытию источников;
- **контроль информационного шума:** слишком широкие, нерелевантные и ошибочно извлечённые объекты для проверки входного фильтра.

Исторические признаки рассчитываются автоматически по датированным документам. Один feature builder используется для организаторских строк, отрицательных примеров и новых кандидатов. Организаторские объяснения и вручную выбранные ссылки не заменяют этот расчёт.

Основная оценка проводится через stratified grouped 5-fold cross-validation. Отчёт содержит Accuracy, Precision, Recall, F1, confusion matrix, ошибки по типам отрицательных примеров и результаты по технологическим областям. Внутренняя цель — Accuracy не ниже 80%. Метрика на самостоятельно собранном корпусе обозначается как внутренняя и не выдаётся за результат на закрытой выборке организаторов.

Для каждого live-кандидата модель сохраняет полный аддитивный разбор logit:
intercept, значение признака после преобразования, коэффициент и локальный вклад.
Ведущие положительные и отрицательные вклады показываются как ключевые
предикторы, а их полная сумма обязана воспроизводить `model_score`. Пока отдельная
калибровка не выполнена, интерфейс называет число «оценкой модели», а не
вероятностью или процентом уверенности.

Backend запускает тот же `AnalysisApplication`, что и CLI, а готовый
`analysis-result-v2` читает через read-only адаптер, повторно проверяет checksums
и не пересчитывает score или policy. `POST
/api/analyses` создаёт сохраняемый job, `GET /api/analyses/{id}` возвращает его
статус и этапы, а `GET /api/analyses/{id}/result` — сохранённый единый
`analysis-response-v1`. После перезапуска незавершённый job возобновляется, а
готовый результат повторно проверяется по SHA-256. Каждый live-job сохраняет 15
неизменяемых checkpoint-этапов и после сбоя продолжает с первого незавершённого
этапа, не повторяя уже опубликованные API- и LLM-вызовы.
Ошибочный job можно явно продолжить через `POST /api/analyses/{id}/retry`; новый
job и новый workspace для этого не создаются.

В Docker Compose каталог реального результата монтируется только для чтения, а
состояние job хранится в отдельном volume. Web-страница `/result` показывает
TOP-15, все три статуса, локальные факторы модели, Evidence Duel, цитаты и ссылки;
синтетический набор к этому пути не подставляется. Прежние synthetic `/api/coverage`
и `/api/stages` (за флагом `NEXTWAVE_ENABLE_SYNTHETIC_DEMO`) удалены вместе с их страницами.
`GET /api/health` возвращает `{"status": "ok", "mode": "cached_snapshot" | "live"}`, и
интерфейс показывает этот режим до создания job. Типы ответа описаны в
`frontend/src/lib/api.ts`; `backend/test_frontend_contract.py` сверяет их с backend и
`demo/result`.

## Запуск проверенного web-результата

Сначала должен существовать каталог `analysis-result-v2` с пятью файлами:
`manifest.json`, `summary.json`, `top15.json`, `candidates.jsonl` и `result.json`. Backend при
старте повторно проверяет их размер и SHA-256; повреждённый или чужой артефакт
не показывается.

По умолчанию Compose использует проверенный snapshot `demo/result`, поэтому
чистый clone запускается без локальных данных и ключей. Другой каталог передаётся
через host-переменную `NEXTWAVE_RESULT_DIR`:

```powershell
$env:NEXTWAVE_RESULT_DIR = "C:\path\to\analysis-result-v2"
docker compose up --build
```

После healthcheck интерфейс доступен на `http://localhost:8080/result`, API —
на `http://localhost:8000/api/result/current`. Создать сохраняемый job можно через
`POST http://localhost:8000/api/analyses`. Каталог результата монтируется read-only;
API не пересчитывает и не меняет model score, policy или Evidence claims.

По умолчанию Compose остаётся в безопасном режиме `cached_snapshot`, чтобы
проверка интерфейса не тратила внешние квоты. Для произвольного живого запроса:

```powershell
$env:NEXTWAVE_ANALYSIS_MODE = "live"
docker compose up --build -d
```

Live-режиму нужны серверные `NEXTWAVE_OPENAI_API_KEY` и `NEXTWAVE_EXA_API_KEY`;
`NEXTWAVE_OPENALEX_API_KEY` и `NEXTWAVE_MEDIACLOUD_API_KEY` необязательны (без первого
OpenAlex работает анонимно с меньшей квотой, без второго новостной поиск идёт через GDELT).
Ключи задаются в корневом `.env` по шаблону `.env.example`, передаются только backend.
Без обязательных ключей job завершается ошибкой с названием ключа. Checkpoint-артефакты
хранятся в volume `nextwave-analysis-work` и переживают перезапуск контейнера.
Различия режимов и проверку стенда см. в [DOCKER.md](DOCKER.md).

Что остаётся сделать вручную: заполнить `.env` и выполнить один живой прогон запроса
на реальных ключах; метрики модели имеют статус `development_only` и не заменяют оценку на
закрытой разметке.

### Воспроизводимая web-репетиция

На Windows Docker Desktop требует работающий Linux Engine. Если `docker info`
сообщает, что Desktop не может запуститься, установите WSL из PowerShell с
правами администратора командой `wsl --install` и перезагрузите Windows.

После запуска Compose проверка создаёт job для зафиксированного запроса, ждёт
результат, сверяет 120 кандидатов, полный TOP-15 и три policy-статуса. Затем она
убеждается, что другой запрос завершается ошибкой и не получает подставленный
результат:

```powershell
docker compose up --build -d
.\.venv\Scripts\python.exe scripts\web_rehearsal.py
```

Команда печатает ID успешного job. Его сохранность после рестарта backend
проверяется отдельно:

```powershell
docker compose restart backend
.\.venv\Scripts\python.exe scripts\web_rehearsal.py --job-id <JOB_ID>
```

Завершение репетиции:

```powershell
docker compose down
```

## Граница MVP

Квалификационная версия должна воспроизводимо показать:

- импорт 100 положительных строк без изменения исходного XLSX;
- проверенный корпус зрелых и хайповых отрицательных примеров;
- отдельную проверку фильтра информационного шума;
- общий расчёт исторических признаков до заданной даты среза;
- бинарную модель и групповой отчёт качества;
- живой поиск по открытым источникам без списка заранее заданных технологий;
- Evidence Duel, anti-echo и причины исключения зрелых кандидатов;
- один заранее зафиксированный исторический срез;
- русскоязычную выдачу ТОП-15 с проверяемыми источниками;
- запуск на стандартном ноутбуке через Docker Compose.

## Текущий статус

Готовы Python-пакет, доменные контракты, Docker-конфигурация, адаптер положительного класса организаторов, протокол экспертной проверки, неизменяемые snapshots и коннекторы OpenAlex, Crossref и Exa. Exa используется для candidate-level отраслевого enrichment, но не генерирует и не отбрасывает кандидатов до модели. Release-интерфейс читает проверенный единый результат реального запроса; синтетический набор по умолчанию отключён.

Discovery, Candidate Gate, aliases, snapshots, candidate-level OpenAlex/Exa
enrichment, point-in-time признаки, frozen inference и resumable Evidence executor
реализованы. Gate проверяет только конкретность и релевантность технологии;
бинарная модель отдельно отличает weak signal от reviewed mature/hype. Один
реальный запрос по инфраструктуре ИИ проверил 1 683 извлечённых названия. После
Gate, объединения вариантов и проверки контрактов в итоговом результате осталось
120 уникальных кандидатов и 5 610 уникальных документов. Все кандидаты получили
scientific+industry enrichment и frozen model score; после Evidence Duel и policy
64 темы исключены, 56 оставлены для наблюдения, а 15 наиболее перспективных из
них показаны отдельным ранжированным списком без изменения настоящего статуса.
Текущий model score некалиброван и поэтому не показывается как вероятность или
процент уверенности.
Перед TOP-15 результат схлопывает только очевидные варианты одной темы: регистр,
дефисы, простой plural и хвостовой акроним вроде `Digital Twins (DTw)`.
Проигравшая карточка получает `reason=duplicate`, `duplicate_of` и имя основной
карточки. Семантические сокращения вроде `RAG` и полной формы автоматически не
объединяются. Ограничение 30 относится к одной рабочей пачке Evidence и не
отбрасывает остальных кандидатов.

Текущий model report остаётся `development_only`: 100 organizer positives
сопоставлены с 57 mature и 7 ранее принятыми hype, поэтому Accuracy 0.915 нельзя
называть официальной оценкой на скрытом ground truth. Query inference v2 сохраняет
неизменившиеся scores, локальные вклады признаков и глобальные коэффициенты.
Единый финальный JSON, decision policy по объединённым Evidence-страницам,
backend/frontend и PostgreSQL-хранилище analysis jobs готовы. Production Compose
проверен созданием задачи, выдачей результата и полным перезапуском контейнеров.
Единый resumable live-runner подключён к CLI и backend. Compose по умолчанию
использует checked snapshot, а режим `NEXTWAVE_ANALYSIS_MODE=live` выполняет
произвольный запрос и обновляет шесть продуктовых стадий. До релиза остаётся
живая end-to-end репетиция нормального и широкого запросов и отказа источника.

## Локальная проверка основы

Windows PowerShell:

```powershell
py -3.13 -m venv .venv
Set-ExecutionPolicy -Scope Process -ExecutionPolicy RemoteSigned
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -e .
python -m unittest discover -s tests -v
python -m nextwave --version
```

Живые API-ключи хранятся только в локальном `.env` или серверном secret store. `config/hackathon.env` содержит лишь несекретные пары provider/model и endpoint. Docker Compose передаёт секреты только backend; они не включаются во frontend, URL запросов, snapshots и логи. Локальный `.env` остаётся игнорируемой Git настройкой разработчика и подхватывается автоматически: приоритет сверху вниз — переменные процесса, затем `.env`, затем файл настроек.

По умолчанию Media Cloud ищет в дефолтном охвате `NEXTWAVE_MEDIACLOUD_COLLECTION_IDS=34412234,34412118`: API story-list без параметров `ss`/`cs` всегда отвечает 422 (доказано живым прогоном 22.09.2026), глобального поиска без коллекций у него нет. Backend может переопределить набор через ту же переменную; пользовательский интерфейс эту настройку не запрашивает. Английская и русская выдачи загружаются отдельными запросами и объединяются только на уровне кандидатов.

В query-specific candidate enrichment после Gate используется Exa: все принятые кандидаты без предварительного pruning получают отдельные запросы по предыдущему и недавнему временным окнам. Exa возвращает новостные highlights вместе с метаданными, поэтому тот же сохранённый документ можно использовать для построения признаков и последующей Evidence-проверки. Перед признаками фиксированная source policy отделяет новостные, корпоративные, пресс-релизные и блоговые страницы от академических репозиториев; исключённые Exa-документы остаются в аудите. Команда `analysis-enrichment-merge` объединяет научные документы OpenAlex с допустимым Exa-контуром. Media Cloud остаётся в старых воспроизводимых артефактах и discovery-контуре; его сохранённый результат служит базой сравнительного replay, а не скрыто смешивается с Exa.

## Проверка LLM-контура

Query Resolver, извлечение кандидатов, Candidate Gate и Evidence executor используют
одну явно раскрытую модель `GPT-5.6 Luna` (`gpt-5.6-luna`) напрямую
через официальный OpenAI API. Все три пары
`NEXTWAVE_LLM_*`, `NEXTWAVE_GATE_LLM_*` и `NEXTWAVE_EVIDENCE_LLM_*` зафиксированы
как `openai / GPT-5.6 Luna`. Это фиксированная конфигурация, а не автоматический routing;
пользователь
интерфейса ничего не выбирает и не вводит. Провайдер и модели зафиксированы в
`config/hackathon.env`; API-ключ является серверным секретом и не передаётся во
frontend, prompt, snapshots или логи. OpenRouter и другие посредники не используются.
Ни один этап не выполняет скрытый fallback:
ошибка становится `review` или неизвестным покрытием.
Evidence дополнительно проверяет точную пару `openai / GPT-5.6 Luna` (старую
квалификационную пару YandexGPT Pro 5.1 можно воспроизводить только для сохранённых
корпусных артефактов). При локальном запуске
нужно использовать `config/hackathon.env`; секреты из `.env` подхватываются
автоматически, поэтому передавать `.env` через `--env-file` нельзя.

CLI читает настройки слоями: `config/hackathon.env`, затем локальный `.env`, затем переменные
процесса. Docker Compose явно передаёт OpenAI, OpenAlex и Exa credentials из локального
`.env` в backend поверх `config/hackathon.env`, поэтому CLI и сервис используют один аккаунт.
Команда проверки:

```powershell
python -m nextwave query-resolve --query "Технологии в ИИ"
```

Для live-запуска backend должен получить `NEXTWAVE_OPENAI_API_KEY`; официальный endpoint
`https://api.openai.com/v1/chat/completions` зафиксирован в адаптере. В развёрнутом сервисе эти значения задаются один раз на сервере;
пользователь интерфейса ничего не регистрирует и не вводит. Тесты и синтетический UI не
требуют доступа к OpenAI.

### Получение прямого OpenAI API key

1. В OpenAI Platform откройте **API keys** и создайте project key.
2. Пополните баланс проекта и убедитесь, что модели `gpt-5.6-luna` доступны аккаунту.
3. Добавьте ключ только в локальный `.env`:

   ```dotenv
   NEXTWAVE_OPENAI_API_KEY=sk-...
   ```

4. Endpoint менять нельзя: runtime обращается напрямую к `api.openai.com`; OpenRouter и другие посредники не используются.
5. Перед полным прогоном выполните один дешёвый smoke-вызов:

   ```powershell
   .\.venv\Scripts\python.exe -m nextwave query-resolve `
     --query "Инфраструктурные технологии для обучения и инференса ИИ" `
     --env-file config/hackathon.env
   ```

Ключ никогда не добавляется в Git. Модельный ID фиксирован в адаптере как `gpt-5.6-luna`; смена модели требует изменения раскрытой конфигурации и повторной проверки качества.
Docker Compose запускает frontend, FastAPI и PostgreSQL. API сохраняет jobs и
их точный итоговый JSON в PostgreSQL и восстанавливает их после полного рестарта.
Полный продуктовый конвейер запускается одной resumable-командой:

```powershell
python -m nextwave analysis-run `
  --query "Инфраструктурные технологии для ИИ" `
  --analysis-id analysis-ai-001 `
  --workspace runtime/analysis-jobs/analysis-ai-001
```

Команда и backend используют один `AnalysisApplication`: discovery, Candidate
Gate, OpenAlex/Exa enrichment, признаки, frozen model, Evidence Duel и единый
результат. Уже опубликованные checkpoint-артефакты сверяются по checksum и
переиспользуются; незавершённая стадия выполняется снова.

Аварийный предел Candidate Gate является вычислительной границей live-сервиса,
а не заявлением о полноте интернета. Если он достигнут, продукт продолжает анализ
по реально проверенным Gate-кандидатам и показывает число проверенных Gate-предложений,
кандидатов и источников, прошедших дальше. Отношение checked/total не входит в пользовательский
результат; точные пропущенные proposal ID остаются в audit manifest.
Экспорт обучающего корпуса строже: частичный Gate туда по-прежнему не допускается.

Результат содержит исходный и нормализованный запрос, варианты поиска, ширину намерения,
провайдера, модель, рассмотренные элементы таксономии OpenAlex и выбранный `subfield` или
`topic`. Ключ не выводится и не сохраняется. Другой файл настроек можно передать через
`--env-file`.

## Сборка организаторского датасета

Исходный файл поместите в `data/raw/organizer_signals.xlsx`, затем из корня репозитория выполните:

```powershell
python -m nextwave dataset-build --input data/raw/organizer_signals.xlsx
```

Команда проверяет лист, заголовки, 100 строк, нумерацию, обязательные значения, области, баллы и отсутствие формул. Только после полной проверки она создаёт новый каталог `data/processed/organizer-positive-2026-09-15-v1` с файлами:

- `positive_candidates.jsonl` — идентификационные поля и положительная метка;
- `positive_annotations.jsonl` — экспертные поля, запрещённые для входа бинарной модели;
- `manifest.json` — версии, диапазон строк, соответствие столбцов, размеры и SHA-256.

Существующий каталог результата не перезаписывается. Для отдельной проверочной сборки можно указать другой новый путь через `--output`.

## Экспорт очереди разметки

После одного или нескольких `discovery-run` соберите очередь экспертной проверки:

```powershell
python -m nextwave labeling-export --runs data/development/discovery/<run_id> --output data/development/labeling-export-v1
```

Команда читает слоты из `templates/labeling_workbook.xlsx`, раскладывает кандидатов, шум и черновики доказательств из сейфов и публикует новый каталог: заполненная книга, `negative_candidates.jsonl`, `noise_controls.jsonl`, `manifest.json` с версиями, составом, дефицитами и контрольными суммами. Шумовые слоты задают только ID и плановый тип (строгие квоты 10/10/10/10/10); фактические область и scope каждой строки берутся из discovery-прогона выбранного объекта и распределяются round-robin между доступными областями. Повтор из тех же входов даёт те же JSONL, книгу и опись побайтово (метки времени zip нормализованы при экспорте); существующий каталог не перезаписывается. В книгу попадают только голубые клетки, метки ставит человек.

## Данные и секреты

Исходный датасет, собранные документы, обученные модели, локальные базы и постоянные секреты не коммитятся. Для приватного квалификационного репозитория временные отзываемые ключи хакатона хранятся только в `config/hackathon.env`, не передаются во frontend и отзываются после оценки. Контактный email для вежливого пула OpenAlex (`NEXTWAVE_OPENALEX_MAILTO`) секретом не является: он штатно уходит открытым параметром запроса. Бесплатный ключ OpenAlex (`NEXTWAVE_OPENALEX_API_KEY`) повышает дневной бюджет: он хранится только в локальном `.env`, отправляется заголовком `Authorization: Bearer` вместе с mailto и никогда не попадает во frontend, URL, snapshots, manifests, результаты или логи. Ключ Exa (`NEXTWAVE_EXA_API_KEY`) также хранится только локально и отправляется заголовком `x-api-key`; он не входит в тело запроса, request identity, snapshots, manifests или сообщения ошибок. Релиз фиксирует checksum исходных данных, версии разметки, признаков и модели, параметры оценки и команду воспроизведения результата.
