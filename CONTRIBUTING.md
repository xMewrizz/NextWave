# Правила разработки

## Единица работы

Каждая задача бэклога выполняется в короткой ветке и обычно оформляется одним pull request. Постоянные ролевые ветки не используются.

Примеры:

- docs/v1-01-project-base
- chore/v1-02-foundation
- feat/v1-05-features
- fix/source-timeout
- release/v1-qualification

Ветка создаётся от обновлённой main. Задача считается выполненной только после получения проверяемого результата, указанного в [ROADMAP.md](ROADMAP.md).

## Коммиты и pull requests

Сообщение коммита кратко описывает изменение:

```text
docs: align qualification scope with organizer guidance
feat: add candidate feature contract
test: cover excluded candidate validation
fix: isolate source timeout failure
```

Pull request содержит:

- решаемую проблему и получившееся поведение;
- изменённые контракты или версии данных;
- реально выполненные команды и сценарии проверки;
- измеренные результаты при наличии;
- оставшиеся ограничения;
- ссылку на задачу бэклога.

Утверждения об обученной модели, достигнутой точности и работающем развёртывании сопровождаются воспроизводимой командой и результатом.

## Владельцы

- ML Engineer проверяет изменения меток, признаков, входов модели, протокола оценки, объединения кандидатов, фильтра зрелости и ранжирования.
- Software Engineer проверяет коннекторы, хранение, jobs, API, интерфейс и развёртывание.
- Оба владельца проверяют общие схемы, pyproject.toml, интеграционное поведение и конфигурацию выпуска.

## Локальные проверки

Для основы проекта выполняются:

```powershell
python -m unittest discover -s tests -v
python -m compileall -q src tests
python -m nextwave --version
```

Новые проверки добавляются вместе с реализованным поведением. Пустые тесты, неиспользуемые CI jobs и декоративные badges не добавляются.

## Данные и артефакты

- Исходные данные не перезаписываются при обработке.
- Evaluation data организаторов, development data и runtime-источники различаются.
- Каждая development-метка хранит происхождение и версию rubric.
- Большие исходные файлы, корпуса, модели, индексы и локальные базы остаются вне Git без явного разрешения на публикацию.
- Маленькие синтетические fixtures допускаются, если проверяют реальный контракт или ошибочный сценарий.
- Секреты хранятся в переменных окружения и не попадают в коммиты, логи и notebooks.

## Публичная документация

В репозитории используются шесть публичных документов:

- README.md
- PROBLEM.md
- REQUIREMENTS.md
- ARCHITECTURE.md
- ROADMAP.md
- CONTRIBUTING.md

Новый публичный документ добавляется только при наличии отдельной задачи репозитория, которую нельзя понятно закрыть существующей структурой.

## Выпуск

Квалификационный релиз фиксирует:

- Git commit;
- manifests датасета и development-разметки;
- версии признаков и модели;
- файл метрик;
- проверенный демонстрационный запрос;
- команду развёртывания;
- известные ограничения.

После release candidate принимаются только изменения, закрывающие квалификационный блокер или критическую ошибку. Настройка модели после официального скрытого результата не смешивается с первоначальной оценкой.
