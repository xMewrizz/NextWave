# Правила разработки

## Единица работы

Одна задача бэклога выполняется в короткой ветке и получает проверяемый результат из [ROADMAP.md](ROADMAP.md). Изменение общего контракта согласуют ML Engineer и Software Engineer.

Примеры веток:

- `feat/v1-03-dataset`
- `feat/v1-04-negative-data`
- `feat/v1-05-features`
- `fix/source-timeout`
- `release/v1-qualification`

## Коммиты и pull requests

Сообщение коммита описывает результат:

```text
docs: define product methodology and acceptance criteria
feat: add grouped cross-validation report
test: cover duplicated press-release chain
fix: isolate source timeout failure
```

Pull request содержит:

- проблему и новое поведение;
- изменённые контракты или версии данных;
- реально выполненные проверки;
- измеренные результаты при наличии;
- ограничения;
- ссылку на задачу бэклога.

Утверждения о точности, работающем поиске и развёртывании сопровождаются командой воспроизведения и сохранённым результатом.

## Владельцы

- ML Engineer проверяет target, разметку, признаки, модели, оценку, aliases, фильтр и ranker.
- Software Engineer проверяет коннекторы, provenance, хранение, jobs, API, интерфейс и развёртывание.
- Оба проверяют общие схемы, интеграцию, Evidence Duel, anti-echo и выпуск.

## Локальные проверки

Базовый набор:

```powershell
python -m unittest discover -s tests -v
python -m compileall -q src tests
python -m nextwave --version
```

Тест добавляется, если он проверяет существенный контракт, ошибочный сценарий или защиту от регрессии. Декоративные тесты, повторяющие реализацию, не добавляются.

## Данные

В проекте различаются:

- `organizer_positive` — 100 подтверждённых организаторами слабых сигналов;
- `team_negative` — проверенные командой mature, hype и noise;
- `runtime_source` — документы, полученные при открытом поиске;
- `synthetic_test` — маленькие fixtures только для проверки кода.

Правила работы:

- исходные файлы не перезаписываются;
- каждый набор получает checksum или manifest;
- ручная метка хранит автора, дату, `cutoff_date`, rubric и источники;
- `draft` и `synthetic_test` не обучают модель;
- aliases и близкие варианты имеют общий `group_id`;
- сведения после `cutoff_date` не влияют на историческую метку;
- большие корпуса, модели, индексы и локальные базы остаются вне Git без отдельного решения;
- секреты не попадают в код, логи и notebooks.

## Эксперименты

Каждый модельный эксперимент фиксирует:

- версии положительного и отрицательного корпусов;
- версию feature builder;
- алгоритм, параметры и seed;
- grouped 5-fold splits;
- out-of-fold предсказания;
- Accuracy, Precision, Recall, F1 и confusion matrix;
- ошибки по `mature`, `marketing_hype` и `noise`.

Модель сравнивается с majority и rule-based baseline на одних folds. Финальная модель обучается на всех проверенных данных только после выбора признаков, алгоритма и порога. Метрика на тех же данных после изменения решения пересчитывается и версионируется; лучший случайный прогон не выбирается вручную.

## Источники и объяснения

- Один URL не равен одному независимому доказательству.
- Перепечатки связываются с предполагаемым origin.
- Важный вывод содержит ссылку и фрагмент или locator.
- LLM-резюме не добавляет фактов, которых нет в сохранённом evidence.
- `unknown` не заменяется нулём без явного правила.
- Рекламный материал может участвовать в discovery, но не быть единственным основанием `main`.

## Публичная документация

В репозитории используются шесть основных документов:

- `README.md` — краткий вход и запуск;
- `PROBLEM.md` — проблема и продуктовая гипотеза;
- `REQUIREMENTS.md` — требования и приёмка;
- `ARCHITECTURE.md` — технические и ML-решения;
- `ROADMAP.md` — порядок задач и сроки;
- `CONTRIBUTING.md` — правила работы.

Подробности реализации размещаются рядом с кодом или артефактом. README не дублирует полное ТЗ, user stories и журнал решений.

## Выпуск

Квалификационный релиз фиксирует:

- Git commit;
- checksums и manifests данных;
- версию rubric и групп разбиения;
- версии признаков и модели;
- отчёт метрик и out-of-fold предсказания;
- проверенный демонстрационный запрос;
- команду чистого развёртывания;
- известные ограничения.

После release candidate принимаются только исправления квалификационного блокера или критической ошибки.
