# Требования

## Версии

| Версия | Назначение | Срок |
| --- | --- | --- |
| MVP v1 | Квалификационная версия для промежуточной сдачи | 29 сентября 2026 года |
| MVP v2 | Финальная версия после прохождения отбора | По расписанию финала |

MVP v1 считается готовым только после проверки полного пути: открытый запрос → реальные источники → новые кандидаты → признаки → модель → фильтр → ТОП-15 → карточка с доказательствами.

## Контракт организаторского датасета

Предоставленная таблица содержит 100 подтверждённых слабых сигналов и не содержит отрицательных примеров. Все строки получают:

- `label = weak_signal`;
- `target = 1`;
- `label_origin = organizer_confirmed`;
- `cutoff_date = 2026-09-15` для первой версии данных;
- ссылку на номер исходной строки, checksum и версию файла.

Исходный XLSX не изменяется. Значение `cutoff_date` хранится в manifest и меняется только при выпуске новой версии организаторского набора.

Следующие поля являются экспертными аннотациями и не входят в бинарную модель:

- «Почему это слабый сигнал»;
- «Стадия развития»;
- «Тренд упоминаний»;
- «Балл (стадия+тренд)»;
- порядковый номер строки;
- вручную приложенные организаторами ссылки.

Эти поля сохраняются для аудита, анализа ошибок и отдельного сравнения с результатами системы. Они не заменяют признаки, восстановленные по открытым источникам.

## Артефакты адаптера V1-03

Адаптер не создаёт модельные признаки и не обучает модель. Он проверяет структуру исходного XLSX и детерминированно создаёт два JSONL-файла и один manifest. Разделение файлов физически отделяет идентификационные данные кандидата от экспертных подсказок организаторов.

### `positive_candidates.jsonl`

Одна строка описывает один подтверждённый организаторами положительный кандидат.

| Поле | Тип | Назначение |
| --- | --- | --- |
| `schema_version` | string | Версия структуры записи, первая версия — `organizer-positive-v1` |
| `record_id` | string | Стабильный идентификатор `organizer-001`…`organizer-100` |
| `source_row` | integer | Физический номер строки в исходном XLSX |
| `canonical_name` | string | Название технологии из таблицы после удаления лишних пробелов |
| `domain` | string | Исходная область организаторов |
| `analysis_scope_key` | string | Стабильный ключ широкой области для последующего исторического знаменателя |
| `aliases` | array[string] | Проверенные альтернативные названия; первоначально пустой список |
| `group_id` | string | Группа связанных названий; до ручной проверки равна `record_id` |
| `identity_status` | string | `pending_review` до проверки aliases и объединения близких технологий |
| `label` | string | Всегда `weak_signal` для предоставленных 100 строк |
| `target` | integer | Всегда `1` |
| `label_origin` | string | Всегда `organizer_confirmed` |
| `cutoff_date` | date | `2026-09-15` для первой версии набора |

Соответствие областей ключам scope фиксируется в версии адаптера:

| Область | `analysis_scope_key` |
| --- | --- |
| Edge | `edge-v1` |
| Защита ИИ | `ai-security-v1` |
| Индустриальный ИИ | `industrial-ai-v1` |
| Инфраструктура ИИ | `ai-infrastructure-v1` |
| Роботы | `robotics-v1` |
| Финтех | `fintech-v1` |

Пример записи:

```json
{"schema_version":"organizer-positive-v1","record_id":"organizer-001","source_row":3,"canonical_name":"Название технологии","domain":"Финтех","analysis_scope_key":"fintech-v1","aliases":[],"group_id":"organizer-001","identity_status":"pending_review","label":"weak_signal","target":1,"label_origin":"organizer_confirmed","cutoff_date":"2026-09-15"}
```

### `positive_annotations.jsonl`

Файл хранит исходные экспертные сведения. Feature builder и модель не имеют права читать его.

| Поле | Тип | Назначение |
| --- | --- | --- |
| `schema_version` | string | Версия структуры — `organizer-annotation-v1` |
| `record_id` | string | Связь с записью в `positive_candidates.jsonl` |
| `source_number` | integer | Значение столбца «№» |
| `companies_raw` | string | Исходное содержимое столбца «Компании» без интерпретации |
| `expert_rationale` | string | «Почему это слабый сигнал» |
| `expert_stage` | string | Исходная стадия развития |
| `expert_mention_trend` | string | Исходное описание тренда упоминаний |
| `expert_score` | integer | Балл организаторов от 3 до 7 |
| `sources_raw` | string | Исходное содержимое столбца «Источники» |

Сохранение значений с суффиксом `_raw` означает, что адаптер не исправляет компании, ссылки и экспертные формулировки молча. Их нормализация выполняется отдельным проверяемым этапом.

### `manifest.json`

Manifest описывает происхождение и состав версии набора:

- `dataset_version` и `adapter_version`;
- имя, размер и SHA-256 исходного XLSX;
- лист `Слабые сигналы`, строку заголовков и диапазон данных;
- точное соответствие исходных заголовков выходным полям;
- `cutoff_date`;
- количество входных, принятых и отклонённых строк;
- имена и SHA-256 двух выходных JSONL-файлов;
- список ошибок проверки, который пуст для успешной сборки.

Одинаковые XLSX, версия адаптера и cutoff должны создавать побайтно одинаковые JSONL-файлы. Время запуска не входит в версию датасета. При несовпадении листа, заголовков, числа строк, обязательного значения или допустимого диапазона балла адаптер завершается с ошибкой и не оставляет частичный результат.

`positive_candidates.jsonl` не передаётся бинарной модели напрямую. Feature builder читает идентификатор, название, проверенные aliases, scope и cutoff, затем создаёт отдельный FeatureVector. Поля `label` и `target` используются только при сборке обучающей выборки; у кандидатов открытого поиска их нет.

## Обучающие и проверочные наборы

### Положительный класс

Положительный класс состоит из 100 строк организаторов. Для каждой строки адаптер формирует каноническое имя, область, исходные названия, `group_id` и поисковую формулировку. Автоматически предложенные синонимы проверяются человеком до исторического обогащения.

### Модельный отрицательный класс

Минимальный отрицательный корпус содержит **100 проверенных кандидатов**:

- 50 зрелых технологий;
- 50 примеров маркетингового хайпа вокруг конкретной технологии.

Отрицательные примеры распределяются по шести областям организаторского набора. Они используют ту же дату среза, те же коннекторы и тот же feature builder, что и положительный класс. Простые отрицательные примеры с очевидными словами-маркерами не должны составлять основную часть корпуса.

`mature` назначается, когда к дате среза подтверждено массовое внедрение, сформированный рынок, отраслевой стандарт либо устойчивое конкурентное разделение. `marketing_hype` назначается конкретной технологии, если сильный информационный рост не подтверждён независимыми техническими основаниями.

Для воспроизводимой разметки `mature` требует хотя бы одного основания уровня A или B: опубликованного стандарта, подтверждённого серийного внедрения либо устойчивого рынка с несколькими независимыми поставщиками. `marketing_hype` требует наблюдаемой рекламной или новостной волны при отсутствии двух независимых технических origin уровня A или B и подтверждённого пилота к дате среза. Техническим основанием считается только результат, который проверяет конкретную рекламируемую способность, эффект или внедрение кандидата; обзор, концептуальная работа или статья, лишь употребляющая название технологии, таким основанием не является. Анонс, релиз, лабораторная демонстрация или заявление поставщика считается publicity, пока источник явно не подтверждает эксплуатацию в реальной среде или у названного клиента. Пограничная запись остаётся `draft` и не входит в обучение до разрешения разногласия.

### Контроль информационного шума

Отдельный набор содержит не менее **50 объектов** типов:

- слишком широкое понятие;
- нерелевантный запросу объект;
- организация, продукт или рекламное утверждение вместо технологии;
- ошибочно извлечённый фрагмент;
- дубликат существующего кандидата.

Этот набор проверяет входной фильтр и формирование кандидатов. Он не включается в основную метрику бинарной модели, чтобы лёгкие примеры не завышали Accuracy.

Материал для V1-07 отбирается из нескольких выходов discovery, а не только из списка `accept`: исходных упоминаний и предложений, исключений при формировании предложений, ошибок текстового извлечения, решений `reject` и `review` входного Gate, а также спорных сокращений и синонимов, предложенных для проверки. На этапе V1-07 эти записи экспортируются в очередь экспертной проверки вместе с документом, locator и причиной. Из неё отбираются шумовые контроли пяти указанных типов. Невалидное модельное упоминание не становится истинным шумовым примером автоматически; проверяющий должен подтвердить исходный фрагмент и тип ошибки.

`mature` и `marketing_hype` — конкретные технологии, поэтому Gate может пропустить их обе. Для них отбираются предложения по тем же шести областям и источникам, затем выполняются одинаковый исторический поиск и экспертная проверка доказательств на дату среза. Если открытый discovery не даёт нужной квоты класса, выполняется целевой поиск дополнительных конкретных технологий в соответствующих областях; класс нельзя назначать по ответу Gate или по одному заголовку. Автоматический сбор создаёт очередь для review, но сам по себе не гарантирует 50 проверенных записей каждого класса.

### Автоматические поля и решение проверяющего

Конвейер автоматически заполняет устойчивые идентификаторы, каноническое имя и предложенные синонимы, `group_id`, исходный запрос и область, версию `analysis_scope`, дату среза, найденные документы, `origin_id`, предварительно извлечённые evidence, их `direction`, `kind`, `source_type`, `trust_level`, locator и поисковое покрытие.

Проверяющий не собирает эти сведения с нуля. Он подтверждает или исправляет предложенные evidence и сохраняет только экспертную часть:

- аналитический класс либо тип шума;
- краткое основание решения;
- идентификаторы подтверждённых evidence;
- автора и дату проверки;
- статус `draft`, `reviewed` или `adjudicated`;
- версию правил разметки.

В обучение и итоговую оценку входят только записи `reviewed` и `adjudicated`. Второй участник независимо проверяет не менее 20% каждого класса. Разногласие получает итоговую метку и новое обоснование; первоначальные решения сохраняются в журнале.

## Историческое обогащение

Размеченная запись хранит экспертную метку и происхождение, а не готовые модельные признаки. Перед обучением каждый положительный и отрицательный кандидат проходит тот же сбор истории, что и новый кандидат открытого поиска.

Для даты среза `T` используются два основных окна:

- предыдущее: `[T − 730 дней, T − 365 дней)`;
- недавнее: `[T − 365 дней, T]`.

Дополнительный период до пяти лет используется для определения первой найденной даты и долгосрочной зрелости. Документы после `T` исключаются до расчёта любых признаков.

Feature builder рассчитывает:

- число документов в каждом окне;
- число независимых первоисточников в каждом окне;
- долю документов кандидата внутри зафиксированного `analysis_scope` отдельно по каждому количественному источнику;
- изменение этой доли между окнами;
- первую найденную дату и возраст темы;
- число независимых организаций;
- разнообразие типов источников;
- долю зависимых публикаций и перепечаток;
- долю рекламных и низкодоверенных материалов;
- признаки исследования, патента, прототипа, пилота, внедрения, стандарта и сформированного рынка;
- флаги полноты временного покрытия.

Нулевое число документов считается нулём только при успешном покрытии соответствующего окна. Ошибка коннектора или неизвестная дата дают `unknown`. Burst рассчитывается как диагностический признак только при наличии не менее шести покрытых месячных интервалов; он не является обязательным признаком первой модели.

Количественная динамика разных классов источников не складывается в одно число. Публикации и новостные материалы имеют отдельные признаки и отдельные ограничения покрытия.

`analysis_scope` фиксируется до извлечения кандидатов и не меняется в зависимости от их названий. Он хранит исходный пользовательский запрос, каноническую английскую формулировку, варианты поиска, языки, ширину намерения, необязательный фильтр таксономии и версию resolver. Все кандидаты одного запуска используют одинаковый знаменатель. Для обучающего корпуса положительные и отрицательные примеры сопоставляются внутри одного scope. Для демонстрационного запроса выполняется проверка устойчивости результата на заранее заданной широкой и узкой формулировке; сильное изменение рангов отмечается как ограничение.

Query Resolver должен выполнять следующие правила:

- `ИИ` и `Технологии в ИИ` разрешаются в одну широкую область `artificial intelligence`, если пользователь не добавил более узкий смысл;
- русскоязычная формулировка не отправляется как единственный запрос в англоязычный семантический индекс;
- широкая область может получить только фильтр OpenAlex `subfield`, конкретная технология — фильтр `topic`;
- `topic` или `subfield` принимается только при полном покрытии нормализованной формулировки и однозначном лучшем совпадении;
- отсутствие уверенного элемента таксономии не является ошибкой и не блокирует текстовый и семантический поиск;
- недоступность taxonomy API сохраняется отдельно от результата `no_match`;
- интерпретация, рассмотренные элементы таксономии, выбор и версия resolver сохраняются для аудита.

Для интерпретации запроса и структурированного извлечения MVP использует пару
`provider=yandex`, `model=YandexGPT Lite 5` (`NEXTWAVE_LLM_PROVIDER/MODEL`). Candidate Gate
использует отдельно настроенную пару `NEXTWAVE_GATE_LLM_PROVIDER/MODEL`:
`provider=yandex`, `model=YandexGPT Pro 5`. Это две явные конфигурации, а не
автоматический routing и не скрытый fallback; пользователь интерфейса ничего не
выбирает и не вводит. Для обеих нужны серверные
`NEXTWAVE_LLM_API_KEY` и `NEXTWAVE_YANDEX_FOLDER_ID`. ТЗ также разрешает YandexGPT Pro 5,
YandexGPT Pro 5.1, Qwen3.6 35B-A3B, Qwen3 235B и GigaChat 2 Lite/Pro/Max, но разрешённый
список не означает автоматический выбор или готовый адаптер каждого провайдера.

Автоматический выбор модели, OpenRouter и тихое переключение на другой сервис не
используются. Единственное ограниченное исключение — повтор повреждённого JSON Query Resolver
через YandexGPT Pro 5; фактически ответившая модель сохраняется в результате. API-ключ
передаётся только в заголовке запроса, не входит в prompt, результат, snapshot или журнал.
При недоступности LLM Query Resolver возвращает явную ошибку.

## Происхождение и независимость источников

Документы относятся к одной цепочке происхождения, если совпадает DOI, идентификатор патента или канонический URL. При отсутствии устойчивого идентификатора используются ссылка на исходный материал, близость заголовка, издатель и близкая дата публикации.

Количество URL и количество независимых подтверждений хранятся отдельно. Репост, перевод или пересказ не создаёт новое независимое основание.

Уровни доверенности:

| Уровень | Источники | Использование |
| --- | --- | --- |
| A | Научная публикация, патент, стандарт, регулятор, государственный реестр | Основное техническое или рыночное основание |
| B | Университет, научный центр, официальный технический материал компании, аналитический отчёт с методологией | Подтверждающее основание |
| C | Профессиональное отраслевое медиа с автором и датой | Контекст и дополнительное подтверждение |
| D | Пресс-релиз, реклама, блог, социальная сеть, агрегатор | Discovery и индикатор хайпа; не единственное основание `main` |

Уровень доверенности определяется типом и происхождением материала, а не названием домена. Для важного утверждения сохраняются документ, фрагмент и locator.

## Формирование кандидатов

Кандидат должен описывать конкретную технологию, механизм или применение. До модели выполняются:

1. Текстовый экстрактор создаёт общий `CandidateMention` только из проверяемого текста: для OpenAlex — из названия и abstract, для Media Cloud и GDELT — из заголовка и доступного фрагмента исходного материала. OpenAlex topics и keywords не создают кандидатов самостоятельно: их ID и score присоединяются только при точном совпадении с названием, уже найденным в тексте того же документа. Упоминание всегда содержит `document_id`, коннектор и точный locator.
2. Provider hints OpenAlex сохраняют исходные идентификаторы и score, но не добавляются в универсальный `SourceDocument` и не считаются готовыми технологиями. Crossref используется для точечного обогащения найденных DOI; его метаданные не создают второе независимое упоминание той же работы.
3. Упоминания всех discovery-коннекторов с одинаковым названием после нормализации регистра, пробелов, дефисов и подчёркиваний объединяются в один `CandidateProposal` до Gate. Предложение хранит исходные написания, упоминания, документы, независимые `origin_id`, коннекторы и типы извлечения. Название пользовательского scope и точное название организации сразу исключаются с явной причиной.
4. Единый Candidate gate получает научные и информационные предложения текущего запуска, анализирует их вместе с названиями и аннотациями документов, проверяет релевантность запросу и наличие конкретной технологии, механизма или применения. Общие области, методы исследования, организации и рекламные формулировки исключаются.
   Входной Gate реализуется в V1-06 до проверочного поиска. Он фиксирует одно из решений `accept`, `reject`, `review`, код причины, версию метода и документы-основания. Отсутствующий, противоречивый или некорректный ответ не считается принятием. Качество решений оценивается на проверенном корпусе в V1-09.
5. После Gate повторного объединения безопасных написаний нет: оно выполнено на шаге 3. Каждое принятое предложение сохраняет каноническое имя, исходные написания и документы. Предполагаемые сокращения, переводы и смысловые синонимы сохраняются как предложения для review с указанием основания; без подтверждения они не расширяют запрос проверочного поиска.
6. По каноническому имени группы выполняется отдельный verification search; сгруппированные на шаге 3 варианты написания используются при сопоставлении ответа. Только после него объект становится `Candidate` и допускается к сбору evidence и признаков. Кандидат, найденный только в информационном контуре, запускает научную проверку и до её результата не может получить `main`.
   Первый проход ищет работы в OpenAlex по каноническому имени принятой группы с отдельным ограниченным бюджетом и тем же cutoff. Сырой ответ сохраняется; успешный ноль не трактуется как отсутствие технологии во всём научном корпусе, а отказ или пропуск из-за лимита не заменяются нулём. Поисковое совпадение не считается подтверждённым техническим основанием без последующего извлечения и проверки утверждения.
7. Документы первоначального и проверочного поиска группируются по точному `origin_id`. Несколько записей с одним DOI или canonical URL сохраняются для аудита, но дают одну точную группу. Совпадение заголовка новостей при разных URL лишь помечает возможную перепечатку: до проверки нельзя считать её доказанным дублем или независимым событием. Поисковые документы остаются входом для последующего извлечения evidence, а не готовыми подтверждениями.

Перед извлечением из новостей система пытается получить содержимое исходной страницы по URL, обрабатывая до шести страниц одновременно. Для Media Cloud и GDELT фиксируются статусы `article_text`, `meta_description` и `title_only`, хеш полученного содержимого, способ извлечения и факт усечения. `article_text` может использоваться для последующего извлечения проверяемого утверждения. Meta description и заголовок подходят для discovery, но сами по себе не считаются evidence. Ошибка загрузки не удаляет документ и не подменяется пустым успешным результатом.

Из аннотаций научных публикаций и `article_text` система формирует только предложения `EvidenceProposal`: дословная цитата из сохранённого `excerpt`, locator, идентификатор документа и origin, URL, тип утверждения и направление `support`/`counter`. Предложение имеет статус `pending` и не участвует как подтверждённый факт в итоговом решении до проверки. Отсутствие извлечённого утверждения, недоступность текста, ограничение бюджета и ошибка модели сохраняются как разные состояния покрытия. Для точной origin group модель рассматривает не более одного документа; связь разных URL с одним событием проверяется отдельно.

Информационный discovery выполняет английский и русский запросы отдельно в пределах общего бюджета. Media Cloud является основным провайдером и по умолчанию использует дефолтный охват `34412234,34412118` (API story-list без `ss`/`cs` всегда отвечает 422); фиксированные коллекции могут быть переопределены backend-конфигурацией без участия пользователя. GDELT используется только при отсутствии конфигурации Media Cloud или полном отказе его запросов. Успешная пустая выдача Media Cloud не считается отказом. При fallback окно GDELT ArtList ограничивается последними тремя календарными месяцами и явно сохраняется в параметрах запроса.

Текстовый извлекатель обрабатывает весь набор ограниченными пачками: не больше восьми документов и 24 000 символов входного текста на вызов, не больше трёх одновременных вызовов по умолчанию. Модель возвращает только текст упоминания и поле `title` или `excerpt`; система самостоятельно проверяет точное вхождение, вычисляет locator и отклоняет выдуманные или перефразированные названия. Для каждого документа сохраняется покрытие доступного текста и отметка усечения. Пропущенные документы, неизвестные идентификаторы, недоступные поля и повторные упоминания фиксируются отдельными ошибками, а не подменяются пустым результатом.

В обычном запуске Candidate gate проверяет все обоснованные уникальные предложения ограниченными параллельными пачками. Аварийный предел в 1000 предложений защищает сервер, но не считается допустимым завершением поиска. При его достижении в проверку детерминированно и по очереди попадают четыре наблюдаемых слоя: несколько коннекторов, два-три независимых origin, один origin, четыре и более origin; пустой слой отдаёт место остальным. Запуск получает статус `partial`, явно хранит число и ID непроверенных предложений и не допускается к итоговому TOP-15 или обучающей разметке. Слои не являются метками `weak`, `mature` или `hype` и не передаются бинарной модели.

После полного Candidate Gate query-specific enrichment выполняется для каждого принятого кандидата без предварительного pruning. Научный класс формируется из OpenAlex, информационный — из Exa по предыдущему и недавнему временным окнам. Exa не участвует в генерации кандидатов. До расчёта признаков provider-independent source policy исключает академические репозитории и журнальные статьи из информационного класса, сохраняет исключённые документы в аудите и типизирует оставшиеся страницы как industry media, company technical, press release или social/blog. Изменение этой policy требует новой версии контракта и replay; правило не может зависеть от score модели или целевой метки.

Шумовой контроль оценивает этот этап отдельно от бинарной модели.

## Модель и оценка

Первая модель — регуляризованная Logistic Regression на компактных текстовых и структурированных признаках. Она сравнивается с majority baseline и зафиксированным rule-based baseline. Более сложная модель допускается только при улучшении на том же протоколе.

Используется stratified grouped 5-fold cross-validation:

- одна технология и её синонимы целиком находятся в одном fold;
- доли положительного класса, `mature` и `marketing_hype` сохраняются насколько позволяет число групп;
- обучение текстового представления, отбор признаков, настройка параметров и выбор порога выполняются только на обучающей части fold;
- для каждой строки сохраняется одно out-of-fold предсказание;
- после выбора решения финальная модель обучается на всём проверенном бинарном корпусе.

Отчёт содержит:

- Accuracy, balanced Accuracy, Precision, Recall и F1;
- метрики по каждому fold и объединённым out-of-fold предсказаниям;
- confusion matrix;
- Recall на 100 строках организаторов;
- false positive rate отдельно для `mature` и `marketing_hype`;
- результаты по шести технологическим областям;
- перечень ошибок и ограничения корпуса;
- отдельную долю отклонённого шума и долю сохранённых валидных кандидатов.

Оценка шума разделяет ответственность слоёв. Метрика Candidate gate считается
только на `broad_concept`, `irrelevant` и `not_technology`, для которых сохранено
фактическое решение Gate. Ошибки извлечения и дубли учитываются отдельно как
защита extraction validation и alias resolution. Объект без сохранённого решения
Gate уменьшает coverage и не засчитывается как успешное отклонение. Дополнительно
публикуется end-to-end доля шума, не дошедшего до ранжирования.

Дополнительно выполняется stress-test с исключением одной технологической области из обучения. Он не заменяет основную метрику, но показывает зависимость результата от тематического покрытия.

Внутренняя цель — Accuracy не ниже 80%. Поскольку отрицательный класс собирает команда, эта оценка не называется официальным результатом на закрытом датасете.

Выход модели называется `model_score`. Он называется вероятностью или уверенностью только после отдельной проверки калибровки на out-of-fold предсказаниях. В остальных случаях интерфейс использует формулировку «оценка модели».

## Политика итогового решения

Правила применяются в фиксированном порядке:

1. Нерелевантный, неконкретный или дублирующий объект получает `excluded` до модели.
2. Подтверждённый стандарт, массовое внедрение или сформированный рынок дают `excluded` независимо от роста упоминаний.
3. Рекламная волна без независимого основания уровня A или B даёт `excluded`.
4. Непроверенные EvidenceProposal не означают отсутствие maturity/hype и дают
   `watchlist` с причиной `evidence_review_incomplete`.
5. Решение Gate `review`, недостаточное временное покрытие, меньше двух независимых
   цепочек происхождения, меньше двух организаций, отсутствие основания A/B или
   недоступный model score дают `watchlist`.
6. Кандидат, прошедший проверки и модельный порог, получает `main`.
7. Содержательный кандидат ниже модельного порога получает `excluded` с вкладом признаков и причиной.

Для `main` требуется как минимум одно основание уровня A или B, две независимые цепочки происхождения и две независимые организации. Порог модели выбирается только внутри обучающих folds и фиксируется вместе с версией модели.

## Evidence Duel

Карточка кандидата содержит:

- `signal case` — подтверждённые основания новизны, роста, ранней стадии и потенциального преимущества;
- `skeptic case` — подтверждённые основания зрелости, стандартизации, рынка, рекламной волны и информационного эха;
- итоговый статус;
- оценку модели и вклад признаков;
- неизвестные или недоступные данные.

Сгенерированное резюме не добавляет фактов, которых нет в сохранённых наблюдениях.

## Открытый поиск

Система:

- принимает непустой запрос длиной до 200 символов;
- обращается к реальным открытым источникам в момент запуска и не требует предварительно собранного корпуса по всем возможным темам;
- не ограничивает кандидатов строками организаторского датасета;
- использует локальную базу как накопленное хранилище обработанных документов и evidence, а не как полный поисковый индекс OpenAlex или новостного корпуса;
- при каждом новом анализе текущего состояния выполняет ограниченный live-discovery и проверку свежей дельты, даже если по похожему scope уже есть локальные документы;
- до обращения к источникам создаёт версионируемый `DiscoveryPlan`, который фиксирует `analysis_scope`, временное окно и максимальное число запросов, страниц и документов, timeout одного запроса, общий предел времени и обязательность каждого коннектора; фактический расход бюджета сохраняется отдельно;
- использует Crossref точечно для проверки DOI и заполнения отсутствующих метаданных уже найденных работ, а не для дублирования массового discovery;
- считает информационный коннектор заменяемым: его отказ даёт `unknown` для зависимых полей и предупреждение о неполном покрытии, но не превращает отсутствие ответа в отсутствие событий;
- сохраняет параметры запроса, время запуска, ответы коннекторов и версии обработки;
- ограничивает время каждого коннектора и продолжает работу при частичном отказе;
- сохраняет snapshot запуска для воспроизводимости;
- формирует полный результат не дольше трёх минут на демонстрационном ноутбуке при доступных источниках;
- показывает прогресс и явно обозначает неполный результат.

Научный discovery выполняет не более четырёх страниц по стандартному плану: канонический
text search, semantic search, taxonomy search при наличии фильтра и один дополнительный
английский alias. Максимум 100 записей на страницу и 400 записей на запуск являются
ресурсным потолком, а не целевым объёмом. Один документ, найденный несколькими каналами,
сохраняется один раз по `origin_id`; число повторов учитывается отдельно. Фактические запросы,
страницы, принятые документы, ошибки parser и причина остановки входят в результат исполнения.

Точный сохранённый ответ может повторно использоваться при восстановлении оборванного запуска или явном воспроизведении snapshot. Для нового анализа текущего состояния cache hit не отменяет запрос свежести к обязательному источнику. Если OpenAlex недоступен, результат не объявляется полным: система использует сохранённые данные только как частичный результат с датой последнего успешного покрытия.

Для количественной динамики MVP использует один стабильный библиографический источник. Второй независимый контур даёт дополнительный контекст о внедрении, стандартах, рынке и информационной активности, когда соответствующий провайдер доступен. Один и тот же DOI или исходный материал не считается независимым подтверждением при получении через разные коннекторы.

Media Cloud используется как вспомогательный международный новостной индекс. Его `story` означает отдельный новостной или медийный материал по URL, а не научную публикацию. Поле `publish_date` считается оценкой даты публикации, `indexed_date` — моментом наблюдения архивом. API не отдаёт полный текст: запись может участвовать в discovery и временном ряду, но становится evidence только после извлечения проверяемого фрагмента с исходного URL. Для резервных материалов GDELT поле `seendate` также трактуется как момент наблюдения. Информационные признаки остаются `unknown`, если ни один провайдер не подтвердил требуемое покрытие.

Количество документов в поисковой выдаче не используется как сила сигнала: оно зависит от каналов поиска, лимитов и пагинации API. Discovery объединяет текстовые, семантические и тематические результаты только для поиска кандидатов. Количественные признаки строятся отдельными фиксированными запросами и нормализуются внутри каждого источника. Сырое отношение количества материалов информационного источника к количеству работ OpenAlex не рассчитывается.

Англоязычные и русскоязычные новостные результаты не складываются в один счётчик. Для каждой языковой ветви сохраняются отдельные покрытие, число независимых origin groups и нормированная динамика. Отсутствие русскоязычной выдачи означает `unknown`, а не отсутствие события. Кандидат, найденный только в новостях, не получает `main` без независимого технического основания уровня A или B.

Перед включением новостных признаков в бинарную модель сравниваются grouped CV-результаты с ними и без них. Если новостные признаки ухудшают общую метрику, результаты по отдельным областям или устойчивость к исключению технологической области, они исключаются из модели и остаются только в Evidence Duel и интерфейсе.

## API и интерфейс

Интерфейс и аналитическая выдача представлены на русском языке. Для анализа отображаются:

- исходный запрос и дата среза;
- число обработанных документов, независимых origin groups и найденных кандидатов;
- дату последней успешной проверки и статус покрытия каждого источника;
- ТОП-15 кандидатов `main`;
- оценка модели, место в списке и ключевые факторы;
- причины `watchlist` и `excluded`;
- Evidence Duel;
- описание, потенциальное преимущество и подтверждённый кейс;
- источники: название, ссылка, дата, тип, язык, уровень доверенности;
- отметка автоматического перевода или генеративного резюме;
- версии snapshot, признаков и модели.

Иностранное название источника сохраняется. Русскоязычное резюме отделяется от оригинального текста.

Сводный счётчик на главной странице формулируется как «NextWave обработал N документов, M независимых первоисточников и K кандидатов». Он описывает накопленный опыт системы и не называется размером доступного мирового корпуса.

## Исторический срез

До запуска фиксируются кандидат, дата среза, запрос и критерий последующей проверки. Документы после даты среза физически исключаются из входа feature builder и модели. В интерфейсе последующие события показываются отдельно и не меняют сохранённую оценку.

Исторический кандидат не используется для ручной настройки правил после просмотра результата.

## Репозиторий и развёртывание

- Python-зависимости объявлены в `pyproject.toml`.
- Backend и frontend проходят отдельные проверки в CI.
- Docker Compose запускает web-интерфейс, API и PostgreSQL интегрированной версии.
- Сбор, нормализация, признаки, модель, решение и представление разделены в коде.
- Постоянные секреты, исходные корпуса и обученные артефакты не попадают в Git. Для приватного квалификационного репозитория допускается отдельный отзываемый Media Cloud token, ограниченный задачей хакатона и автоматически передаваемый только backend.
- Пользователь web-сервиса и проверяющий клонированного репозитория не регистрируются во внешних источниках и не вводят API-ключи вручную.
- Токен отсутствует во frontend, URL запросов, логах и snapshots и отзывается после завершения оценки.
- Релиз фиксирует один commit, manifests данных, модель, отчёт и демонстрационный snapshot.

## Критерии приёмки MVP v1

- [ ] Все 100 строк организаторов импортированы с target `1` и единым `cutoff_date`.
- [ ] Экспертные поля организаторов отсутствуют во входе бинарной модели.
- [ ] Проверены минимум 50 зрелых и 50 хайповых отрицательных кандидатов.
- [ ] Отдельно проверены минимум 50 шумовых объектов.
- [ ] Положительные, отрицательные и новые кандидаты используют один feature builder.
- [ ] Документы после даты среза не влияют на признаки.
- [ ] Aliases и близкие дубли не пересекаются между folds.
- [ ] Отчёт содержит заявленные метрики, результаты по подтипам и областям.
- [ ] Внутренняя Accuracy достигает 80%; при меньшем результате MVP не считается прошедшим этот критерий, а отчёт анализа ошибок сохраняется.
- [ ] Свободный запрос получает кандидатов из реального live-discovery OpenAlex без предварительной загрузки глобального корпуса.
- [ ] Повтор текущего запроса проверяет свежие данные, а воспроизведение snapshot возвращает зафиксированный результат.
- [ ] Отказ информационного коннектора помечает зависимые признаки как `unknown` и не выдаётся за отсутствие событий.
- [ ] В демонстрационном запросе формируется ТОП-15 новых кандидатов.
- [ ] Перепечатки не увеличивают число независимых подтверждений.
- [ ] Зрелый контроль и рекламная волна не получают `main`.
- [ ] Неоднозначный содержательный кандидат получает `watchlist`.
- [ ] Каждое существенное утверждение связано с источником и фрагментом.
- [ ] Исторический срез исключает будущие документы и воспроизводится.
- [ ] Отказ одного коннектора не прерывает весь анализ.
- [ ] Второй участник разворачивает релиз по README на чистом окружении.

## После квалификации
